Parallelizing a quantum computation simulator

Ayush Garg

Download PDF

Summary

My goal is to parallelize the simulation of a quantum computer using GPUs, with the main focus on speeding up state-vector updates and scheduling the necessary computations as effectively as possible. I plan to implement the simulator from scratch in C++ and CUDA and evaluate it on the GHC machines.

Background

At its core, state-vector simulation of quantum circuits involves keeping track of a complex probability amplitude for every possible arrangement of bits. The squared magnitude of an amplitude gives the probability of observing that bit string. For example, a three-qubit system has the state

|ψ⟩=α0|000⟩+α1|001⟩+α2|010⟩+α3|011⟩+α4|100⟩+α5|101⟩+α6|110⟩+α7|111⟩,∑i=07|αi|2=1. |\psi\rangle = \alpha_0|000\rangle + \alpha_1|001\rangle + \alpha_2|010\rangle + \alpha_3|011\rangle + \alpha_4|100\rangle + \alpha_5|101\rangle + \alpha_6|110\rangle + \alpha_7|111\rangle, \qquad \sum_{i=0}^{7}|\alpha_i|^2=1.

In general, this means maintaining an array of 2n2^n complex numbers for nn qubits. The memory requirement grows exponentially. Using two 64-bit floating-point values per amplitude, a 30-qubit state vector alone requires 16 GiB. Initially, I will use the known computational basis state |0⋯0⟩|0\cdots0\rangle and apply a sequence of quantum gates to evolve it.

In a Boolean circuit, NAND is a universal gate. Similarly, the gate set {H,T,CNOT}\{H,T,\mathrm{CNOT}\} can approximate any unitary quantum circuit to arbitrary accuracy, up to global phase. A finite sequence from this discrete gate set cannot represent every unitary exactly.

The three gates

Hadamard (HH) mixes the amplitudes of |0⟩|0\rangle and |1⟩|1\rangle:

H=12(111−1),H|0⟩=|0⟩+|1⟩2. H=\frac{1}{\sqrt2}\begin{pmatrix}1&1\\1&-1\end{pmatrix}, \qquad H|0\rangle=\frac{|0\rangle+|1\rangle}{\sqrt2}.

Phase (TT) leaves the |0⟩|0\rangle amplitude unchanged and rotates the phase of the |1⟩|1\rangle amplitude:

T=(100eiπ/4),T|0⟩+|1⟩2=|0⟩+eiπ/4|1⟩2. T=\begin{pmatrix}1&0\\0&e^{i\pi/4}\end{pmatrix}, \qquad T\frac{|0\rangle+|1\rangle}{\sqrt2} =\frac{|0\rangle+e^{i\pi/4}|1\rangle}{\sqrt2}.

Controlled NOT (CNOT) flips a target bit when its control bit is 1. In control–target order,

|00⟩↦|00⟩,|01⟩↦|01⟩,|10⟩↦|11⟩,|11⟩↦|10⟩. |00\rangle\mapsto|00\rangle,\quad |01\rangle\mapsto|01\rangle,\quad |10\rangle\mapsto|11\rangle,\quad |11\rangle\mapsto|10\rangle.

For example, CNOT maps (|00⟩+|10⟩)/2(|00\rangle+|10\rangle)/\sqrt2 to the entangled state (|00⟩+|11⟩)/2(|00\rangle+|11\rangle)/\sqrt2.

Opportunities for parallelism

  1. Parallel state-vector updates. A single-qubit gate can update 2n−12^{n-1} disjoint amplitude pairs in parallel. Since the state space can be enormous, assigning these updates to GPU threads offers substantial parallel work.

  2. Independent qubit groups. Groups that start unentangled and do not interact can be simulated separately. For example, starting from |0000⟩|0000\rangle, one worker can apply H(q0)H(q_0) followed by CNOT(q0,q1)\mathrm{CNOT}(q_0,q_1), while another applies H(q2)H(q_2) followed by CNOT(q2,q3)\mathrm{CNOT}(q_2,q_3). Each worker produces a two-qubit Bell state. Their results can be combined by a tensor product when a joint state is needed.

  3. Multiple devices (stretch goal). Distributing the state vector across devices increases the available memory. However, gates that combine amplitudes on different devices require communication. I may not have time to implement this extension.

The challenge

There are many challenges with simulating a quantum computer.

The first and foremost is dealing with the memory requirements. An nn-qubit quantum circuit requires maintaining 2n2^n complex amplitudes, so memory requirements grow exponentially. These large state vectors exceed CPU caches and may exceed GPU memory. This will require me to be very mindful about the memory transfers done during the computation. Furthermore, splitting a state vector across devices or machines increases available memory, but gates that mix amplitudes in different partitions require communication, which can become a bottleneck for the code.

Another large challenge will be dealing with the workload’s memory access pattern. For example, a general single-qubit gate updates pairs of amplitudes whose indices differ by 2k2^k, where kk is the target qubit’s bit position. This produces predictable access patterns, but the spacing between paired amplitudes varies substantially. Scheduling this effectively while being mindful of the threads’ cache locality seems like a worthy problem. I must be very diligent about the memory access pattern since each update performs relatively little arithmetic compared with the data it reads and writes, so memory bandwidth may limit speedup before all available compute resources are utilized.

Finally, this challenge will be difficult just because of how poorly quantum computer simulation scales. Trying to keep up with the exponential scaling will be incredibly difficult and our speedups will only take us so far. Trying to extract as many qubits as possible out of the simulation seems like a fun and worthy challenge when every additional qubit makes our memory problems twice as painful and increases the work per full state-vector pass by a factor of two.

Resources

I plan to use the GHC machines with NVIDIA GPUs for most of the computation. I will start from scratch and use Qiskit’s CPU Statevector implementation as a correctness reference. I do not hope to match the speed of a mature simulator as it also has GPU implementations and likely does much more complex optimizations, but I still hope to get a good speedup.

Goals and deliverables

Plan to achieve

  1. Sequential baseline. Create a correct C++ state-vector simulator supporting HH, TT, and CNOT, together with reproducible benchmark circuits. Validate complex amplitudes against Qiskit on small circuits.
  2. GPU implementation. Implement CUDA kernels for parallel amplitude updates and measure their speedup relative to the sequential implementation on identical circuits and precision.
  3. Scheduling and optimization. Explore gate/kernel fusion and parallel evaluation of independent qubit groups where the circuit permits it. Evaluate how circuit structure and target-qubit positions affect performance.
  4. Application demonstration. If feasible, use the simulator for a small Shor factoring demonstration, targeting a number such as 119. This requires a suitable arithmetic circuit and decomposition of its gates; intermediate measurement and reset may be needed depending on the construction (Beauregard, 2003).

My performance target is 100–250×\times speedup over my single-threaded CPU baseline on sufficiently large workloads. While there are a large number of independent amplitude updates, I worry that memory bandwidth and launch overhead may prevent me from reaching this goal. I also hope that with this speedup I am able to simulate larger quantum circuits that were unfeasible just on the CPU.

To evaluate speedup, I will use a diverse workload to evaluate how the program scales across both the number of qubits and the length of the circuit. In general, I don’t plan to optimize heavily for very niche circuits like those with minimal entanglement.

Hope to achieve

The stretch goal is to distribute one state vector across multiple devices to increase the available memory. Even 30 qubits require 16 GiB in double precision, so additional devices may allow a few more qubits. This might not be worth the effort due to the exponential requirements of the algorithm. For example, even scaling to four different machines with equal memory would only allow for two extra qubits.

Reduced-scope fallback

If progress is slower than expected, then I will ensure that I have correct serial and single-GPU implementations. I might not be able to create as effective schedulers, and I think that I will likely just end up with a lower speedup.

Platform choice

I plan to use C++ for the serial implementation and CUDA for GPU kernels on the GHC machines. I am choosing CUDA since we have worked with it in class and it maps naturally to the many independent amplitude updates required by each gate. When possible, I will also use Thrust to make the code easier to read and faster.
